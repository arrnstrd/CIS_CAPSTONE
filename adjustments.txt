School Admin — Settings & Account UX/UI Revision Prompt

This is the consolidated revision based on the previous implementation and the adjustments discussed afterward.

The main correction is important: do not treat this as another visual cleanup of the existing Settings page. The previous implementation was too close to simply rearranging the old Settings UI. This revision needs to correct the application shell, account entry point, information architecture, and user flow.

1. Core Direction

The intended experience is:

School Admin Dashboard → Profile Account Menu → Settings → Dedicated Settings Experience

Settings should no longer feel like another module inside the School Admin sidebar.

The overall concept is inspired by the account/settings experience of platforms such as YouTube, Google, Facebook, and GitHub, but do not copy their UI literally. Use them only as references for the underlying UX patterns.

The priorities are:

Keep the existing School Admin sidebar structure.
Add a thin top navigation beside/above the main content area only.
Move the School Administrator account controls from the sidebar footer to that top navigation.
Remove Settings from the sidebar.
Open Settings as a dedicated account/settings experience.
Combine Account and Security into one section.
Require re-authentication before saving sensitive account changes.
Keep the current password-change flow, with minor visual improvements.
Fix the School Year layout and centered modal behavior.
Keep the implementation clean and avoid unnecessary redesign of unrelated areas.

When the School Administrator selects Settings from the profile menu, they should enter the dedicated Settings experience.

This should feel like transitioning from the main application into an account/settings area.

It should not feel like clicking another item in the administrative sidebar.

8. Dedicated Settings Experience

The Settings page should have its own lightweight context/layout.

It should retain the CIS visual identity, particularly the blue theme, but it should feel distinct from the normal School Admin dashboard.

The goal is:

Same application identity, different context.

Do not simply place the old Settings content inside another large x-layouts.admin dashboard page and call it a dedicated settings experience.

The implementation should reflect the conceptual separation between:

Application / Administration

and

Account / Settings

Do not create oversized navigation containers.

The School Year section should naturally expand based on its content.

20. UX Frameworks to Apply

Use the following principles when implementing the revision.

Information Architecture

Separate:

Administrative application navigation

from:

Personal account/settings navigation

Progressive Disclosure

Do not expose every form immediately.

Use:

View → Select → Edit → Authenticate → Confirm → Success

Recognition Over Recall

Show the current value of each setting.

For example:

Full Name
School Administrator

rather than forcing the user to open the setting just to discover its current value.

User Control and Freedom

Provide appropriate:

Cancel,
Back,
Continue,
Confirm,
Done

actions during multi-step flows.

Error Prevention

Sensitive account changes should require authentication before the actual update.

Consistency

The top nav, profile menu, Settings page, buttons, typography, and interactions should feel like parts of the same CIS application.

Minimalism

Avoid excessive:

cards,
borders,
shadows,
containers,
decorative components,
unnecessary animations.
21. Implementation Instructions

Before changing the implementation:

Inspect the current School Admin layout.
Inspect the current sidebar structure.
Inspect the existing sidebar footer account controls.
Inspect the current Settings Blade and JS.
Inspect the existing Settings routes/controllers.
Inspect how profile/logout functionality currently works.
Inspect the School Year component and determine why its content is constrained.
Check whether the existing backend can safely support re-authentication before profile changes.

Do not immediately rewrite everything.

First understand the existing implementation and then make the required structural changes.

22. Preserve Existing Functionality

Do not unnecessarily change:

existing backend functionality,
existing School Year CRUD behavior,
existing password functionality,
existing authentication behavior,
unrelated School Admin modules.

If the frontend flow requires a backend adjustment for proper authentication, identify that requirement and implement it safely.

Do not weaken security simply to preserve an existing frontend endpoint.

23. What NOT to Do

Do not repeat the approach from the previous implementation.

Specifically:

Do not merely make the old Settings page prettier.
Do not keep Settings in the sidebar.
Do not keep the School Administrator account area in the sidebar footer.
Do not duplicate the profile controls in both sidebar and top nav.
Do not place the top nav above the sidebar.
Do not push the sidebar downward.
Do not resize/restructure the sidebar around the top nav.
Do not create four Settings tabs.
Do not expose huge forms immediately.
Do not save name/email changes before authentication.
Do not simply restyle the existing School Year table.
Do not keep the broken School Year nested scroll container.
Do not use a top-anchored School Year modal.
Do not redesign unrelated School Admin pages.

→ sees the existing sidebar unchanged
→ sees a thin blue top nav beside the sidebar
→ sees [Initials] School Administrator / email on the right
→ clicks the profile area
→ selects Settings
→ enters a dedicated Settings experience
→ sees only Account & Security / School Year / Preferences
→ edits account information through a proper authenticated flow
→ changes password through the existing progressive flow
→ manages School Year without the broken constrained container
→ sees School Year modals centered properly
