# 6. CRITICAL DATA-FLOW DIRECTION RULE

This is mandatory.

Determine the direction of every data flow from the actual implementation.

Do NOT automatically use bidirectional arrows because two components interact.

There are two fundamentally different cases.

---

## 6.1 UNIDIRECTIONAL DATA FLOW

A unidirectional data flow means that data moves in **one direction only**.

Represent it using a single-headed arrow:

```text
A → B
```

Examples:

```text
External Entity → Process
Process → External Entity
Process → Data Store
Data Store → Process
Process → Process
```

Example:

```mermaid
flowchart LR
    OP["Scanner Operator"] -->|QR Code Payload| P["Process QR Attendance Scan"]
    P -->|Attendance Record| D[("Attendance Logs")]
```

The arrows indicate the actual direction of data movement.

---

# 7. BIDIRECTIONAL DATA FLOW

A bidirectional relationship means that data genuinely moves in **both directions** between the same two components.

Conceptually:

```text
A ↔ B
```

A double-headed arrow may be used only when both directions form a meaningful two-way data exchange.

Example:

```mermaid
flowchart LR
    A["External Entity"] <-->|Request / Response| P["Process"]
```

However:

### DO NOT use a bidirectional arrow merely because:

* the user can perform multiple actions;
* the system displays information to the user;
* both components interact at different stages;
* the relationship exists conceptually in both directions;
* the user submits data and later receives output;
* a process both reads and writes a database.

When the incoming and outgoing information represents two distinct flows, use **two separate unidirectional arrows**.

Example:

```mermaid
flowchart LR
    T["Teacher"] -->|Attendance Verification| P["Classroom Attendance Process"]
    P -->|Attendance Roster and Verification Status| T
```

This is preferable because the two flows have different meanings.

---

# 8. DATA STORE DIRECTION

Apply the same principle to data stores.

### Write only

If a process only creates or updates data:

```mermaid
flowchart LR
    P["Attendance Process"] -->|New Attendance Record| D[("Attendance Logs")]
```

### Read only

If a process only retrieves information:

```mermaid
flowchart LR
    D[("Student Records")] -->|Student Information| P["Attendance Process"]
```

### Read and write

If a process genuinely reads from and writes to the same data store, represent the two operations explicitly:

```mermaid
flowchart LR
    P["Attendance Process"] -->|Create / Update Attendance Record| D[("Attendance Logs")]
    D -->|Existing Attendance Records| P
```

Do not automatically replace these with:

```text
P ↔ D
```

unless the diagram convention being used explicitly requires a bidirectional relationship and the meaning remains clear.

For this project, **separate labeled arrows are preferred** because they make the actual data movement easier to defend.
