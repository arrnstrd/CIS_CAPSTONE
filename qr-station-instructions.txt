# QR STATION UI IMPLEMENTATION

Implement a new **QR Station** page for the existing Laravel application.

This is a NEW PAGE for the live QR scanning operation.

Do not redesign or replace the existing Time-In / Time-Out History page in this task.

The purpose of this page is to provide a live operational interface where a QR scanner sends a QR string to the browser, the system processes it, and the UI immediately shows the result while maintaining a live queue of recent scans.

---

# 1. IMPORTANT EXISTING PROJECT CONVENTIONS

Before creating anything, inspect the existing project structure and reuse the application's existing components and conventions.

The project already uses components such as:

* `x-layout.admin`
* `x-ui.table`

Prefer existing Blade components, layouts, buttons, cards, badges, form controls, and other reusable UI components over creating new equivalents.

Do NOT unnecessarily create custom components when an existing component already provides the required structure.

Use Bootstrap-compatible styling and the application's existing design system.

Do NOT introduce a completely different UI framework or visual style.

---

# 2. CSS AND JAVASCRIPT FILE RULE

Do NOT place large amounts of page-specific CSS directly inside the Blade file.

Do NOT create arbitrary inline `<style>` blocks for the page.

If custom CSS is required, create a dedicated CSS file inside the existing resources CSS structure.

Use a page-specific filename based on the page name.

Example:

`resources/css/qr-station.css`

Likewise, page-specific JavaScript must be separated into its own file.

Example:

`resources/js/qr-station.js`

Do not put extensive page logic directly inside the Blade template.

The Blade page should primarily handle structure and component composition.

Use the project's existing Vite setup and asset conventions.

Before creating the files, inspect how existing pages import or load page-specific CSS/JS and follow that convention.

# 6. LEFT SIDE — LATEST SCAN / FEEDBACK

The left panel is responsible for showing the latest scan result.

The latest scan should be visually prominent.

When a scan occurs, the panel should update immediately.

Possible states include:

* Successful Time-In
* Successful Time-Out
* Late
* Duplicate
* Invalid QR
* Invalid Checkout
* Excess Scan
* Other existing scan/flag statuses used by the system

Do not hard-code unsupported statuses that do not exist in the current application.

Use the application's actual scan result / flag type values where possible.

# 11. SCAN PROCESSING INDICATOR

The left panel should include a small progress/loading indicator during the scan processing state.

This should be very fast.

The intended visual behavior is approximately:

```text
Scan received
     ↓
Processing
     ━━━━━━━━━━━━━━━━━━━
     ↓
Result
```

The progress indicator should feel like a quick confirmation rather than a long loading screen.

It should normally complete in well under one second once the response is received.

Do not artificially delay the interface just to make the animation visible.

The visual should be subtle, such as a thin progress line near the bottom of the feedback panel.

---

# 12. IMPORTANT ABOUT THE PROGRESS LINE

Do not implement a fake long-duration progress bar.

The real scan processing response should determine the actual state transition.

Use the line only as a visual feedback element.

For example:

```text
Processing...
───────────────
```

Then:

```text

```

The system response should remain the source of truth.

---

# 17. LIVE QUEUE BEHAVIOR

The queue should behave like:

```text
New scan
    ↓
Process
    ↓
Add record to top/latest position
    ↓
Update overview counters
    ↓
Update latest-scan panel
```

Do not reload the entire page for every scan.

Use the project's existing frontend approach for real-time or asynchronous updates if one already exists.

If the current implementation does not yet have WebSockets or broadcasting configured, implement the UI in a way that is compatible with the existing backend response flow without introducing an unrelated real-time infrastructure overhaul.

Do not invent a WebSocket system if the project does not currently use one.

# 18. MANUAL QR STRING FALLBACK

The QR Station should also provide a manual fallback.

This is for cases such as:

* QR code is damaged
* QR code has not yet been printed
* Student's physical QR is unavailable
* Admin needs to manually enter a student's existing QR string

The QR string already exists in the student profile/system.

The admin should be able to copy the QR string and paste it into the station.

---

# 19. MANUAL INPUT UI

The manual input should NOT dominate the page.

It should be compact and clearly presented as a fallback.

Example:

```text
Manual QR String

[ Paste QR string here __________________ ] [ Send ]
```

Keep the input visually clean and reasonably small.

Do not make the manual input the largest element on the page.

The primary interaction remains the physical QR scanner.

---

# 20. MANUAL INPUT AND SCANNER INPUT MUST SHARE THE SAME PROCESS

This is critical.

Do NOT create a completely separate backend logic path for manual input.

Both inputs must ultimately send the same QR string into the same scan-processing logic.

Conceptually:

```text
HID QR Scanner
      │
      ├──────────────┐
      │              │
      ▼              ▼
Scanner Input    Manual Input
      │              │
      └──────┬───────┘
             ▼
       Same QR String
             ▼
       Same Processing
             ▼
      Same Result Logic
             ▼
     Same Feedback / Queue
```

If the scanner and manual input provide the same QR string, they should resolve to the same student and produce the same result.

---

# 21. HID SCANNER SUPPORT

The page must be designed to work with generic QR scanners that behave as HID keyboard devices.

Do NOT assume a vendor-specific scanner SDK.

Do NOT require scanner-specific browser APIs.

Do NOT require a proprietary hardware integration.

The scanner's role is simply:

```text
QR Code
   ↓
Scanner decodes QR
   ↓
Scanner types QR string as keyboard input
   ↓
Enter / submission
   ↓
Web application receives QR string
```

The web application should therefore provide an input mechanism that can reliably receive the scanner's keyboard-style input.

---

# 22. SCANNER INPUT HANDLING

The implementation should inspect the existing project and choose the least invasive approach for receiving HID scanner input.

The page should:

* Be ready to receive scanner input
* Handle the scanner's terminating Enter behavior if present
* Avoid forcing the operator to click an input before every scan
* Recover focus appropriately after a scan
* Avoid interfering with the manual input field

Do not create a confusing visible giant text box specifically for the scanner if the scanner can operate through a focused input mechanism.

The operator should be able to repeatedly scan students without manually resetting the interface each time.

---

# 23. AUDIO FEEDBACK

```text

Successful Time-Out → different success sound
Late                → warning sound
Duplicate           → duplicate sound
Invalid QR           → error sound
```

Use only statuses actually supported by the existing system.

Do not create arbitrary business logic just to create additional sounds.
